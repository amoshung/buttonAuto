# AI 工程助理 計劃書

> 狀態：§9 Q1–Q5 已確認（2026-11-13）；P0、P1 完成（觀察模式驗收中）；P2 待開始。

## 1. 目標

把「智慧按鈕精靈」改成 **AI 工程助理**。它坐在使用者旁邊，代替使用者盯著 Kiro / Antigravity 的 AI 代理：

1. 用**虛擬點擊**（UI Automation Invoke，不動實體滑鼠）點按鈕，並在它判斷出的聊天輸入框輸入文字。
2. 只操作使用者**勾選**的視窗，每個視窗清楚顯示開的是哪個專案。
3. 每個視窗有自己的 `progress.md`，記錄目標、進度、證據與下一步。
4. 讀聊天側邊欄了解進度，持續 prompt 代理朝專案目標前進。
5. 要求代理提出「已達成」的證據並自行查核，不盲信，防止做出空殼。
6. 根據代理的回應決定下一步；適合時直接請代理「自己判斷最佳做法並執行」。

### 不在範圍內（第一版）
- Kiro、Antigravity 以外的 App（VS Code、終端機等）。
- 替使用者做產品方向、需求取捨這類決策（一律交給使用者）。
- 真正的「第二個游標」：Windows 只有一個系統游標，見 §5.5。

## 2. 名詞

| 名詞 | 意思 |
|---|---|
| 工作階段（session） | 一個被勾選的 IDE 視窗＋它開啟的專案。助理只對工作階段動手 |
| 代理 | Kiro 或 Antigravity 內建的 AI（被助理 prompt 的對象） |
| 完成定義 | 可檢查的驗收條件清單，用來判斷目標是否真的達成 |
| 證據 | 能獨立查核的東西：測試指令與完整輸出、檔案路徑與行號、git commit / diff |

## 4. 視窗、專案與授權

### 4.1 辨識專案
實測資料來源：
- 視窗標題：Kiro 是 `檔名 - 專案 - Kiro`；Antigravity 是 `專案 - Antigravity IDE - 檔名`，遠端是 `專案 [SSH: 主機] - Antigravity IDE - …`。
- `%APPDATA%\Kiro\User\workspaceStorage\*\workspace.json`、`%APPDATA%\Antigravity IDE\User\workspaceStorage\*\workspace.json` 記錄資料夾完整路徑（例如 `file:///d%3A/_AI_Projs/buttonAuto`；遠端為 `vscode-remote://ssh-remote+<主機>/home/...`）。

做法：從標題取出專案名稱，再對照 workspaceStorage 找出完整路徑。面板顯示成：

```
☐ Kiro         │ buttonAuto        │ D:\_AI_Projs\buttonAuto
☐ Antigravity  │ y6p2web2          │ D:\@_ZabbixNetBox\y6p2web2
☐ Antigravity  │ bofmgr            │ SSH: BOF456_NewServer:/home/bofmgr   ⚠ 遠端，無法在本機查核證據
```

同名專案有多個候選路徑時，標示「路徑不確定」，讓使用者手動指定。

### 4.2 授權規則
- 偵測到的視窗**預設不勾選**；只有勾選的視窗會被點擊或輸入。這個規則也套用到現有的「UIA 按鈕模式」（目前是所有符合的視窗都會點）。
- 勾選記錄以「App＋專案路徑」為鍵，不用視窗代碼（hwnd 重開就變）。同一個專案關掉重開後，自動對回原本的工作階段，但仍要使用者勾選一次才恢復操作。
- 動手前再確認一次：視窗仍存在、標題裡的專案沒變、仍是勾選狀態。任何一項不符就不動作。

## 5. 工作階段的運作

### 5.1 progress.md
每個工作階段一份。範本：

```markdown
# 進度：buttonAuto（Kiro）
專案路徑：D:\_AI_Projs\buttonAuto
## 目標
（使用者確認過的一段話）
## 完成定義
- [ ] 條件 1（如何查核：…）
- [ ] 條件 2（如何查核：…）
## 目前狀態
階段 / 代理正在做什麼 / 最後更新時間
## 里程碑 commit
| 時間 | 分支 | commit | 內容 | 查核 |
|---|---|---|---|---|
| 2026-11-13 16:40 | feature/export | abc1234 | 匯出功能＋測試 | ✅ git log 確認存在 |
## 已查核的證據
- 2026-11-13 16:40 條件 1：`python -m pytest -q` 26 passed；故意弄壞 `build_report()` 後 3 個測試失敗，改回後全過（commit abc1234）
## 代理宣稱、尚未查核
- 「已完成匯出功能」→ 已要求提供測試輸出與檔案位置
## 下一步
## 待使用者決定
## 互動摘要（最近 20 筆，完整紀錄在 history.jsonl）
```

存放位置待決定（§9 Q2）。完整互動記錄另存 `history.jsonl`，每一筆包含時間、讀到的代理訊息摘要、決策、送出的 prompt、查核結果。

### 5.2 目標與驗收 spec
0. **已在進行中的專案先問代理**：助理第一次接手一個工作階段時，若代理已經在做事，先請代理說明「目前開發的最終目標、已完成的部分、剩下的工作」，整理後交給使用者確認或修改，成為這個工作階段的目標。
1. **使用者訂目標**：在面板上為每個工作階段輸入目標。沒有目標的工作階段，助理不會主動 prompt。
2. **助理與代理討論出驗收 spec**：助理把目標交給代理，請它提出詳細、可檢查的驗收條件（每一條要寫怎麼驗證、跑哪個測試）。助理逐條檢查是否具體、可驗證、和目標一致，不夠具體就要求修改，直到定稿。
3. **正在進行的計畫由使用者勾選或代理判斷**：助理列出專案內的 plan / progress 文件與 Kiro spec 當候選，由使用者勾選哪些正在進行，或請代理判斷（代理的判斷只能從候選清單中選，且要使用者採用才生效）。確認後，驅動器只以這些文件判斷進度。
4. 候選來源：**專案內的 plan / progress 文件**（`docs/plans/`、`PROGRESS*.md`、`*plan*.md` 等，依修改時間由新到舊；最新的往往才是代理真正在執行的工作，spec 可能已過時），以及 Kiro 專案的 `.kiro/specs/*/requirements.md`、`tasks.md`（實測 MMI_Kernel_Origin、y6p2web2 都有）。`tasks.md` 的勾選是代理自己勾的，只當進度參考，不算證據。
5. 定稿的驗收 spec 寫進 progress.md 的「完成定義」，並通知使用者。

### 5.3 驅動迴圈
每個勾選的工作階段各自執行。

**節奏規則**
- **只在代理閒下來時才發 prompt**：代理工作中（畫面有 Working、轉圈、Cancel）一律不插話；等它停下來、讀完它的回應，才決定下一步。
- **代理在等允許時不送訊息**：畫面上有 Allow / Deny 等按鈕時，代理不會處理新訊息。助理改成提示「代理在等你允許」並提供代按按鈕（觀察模式下由你按；非觀察模式依危險規則與風險門檻自動處理），避免雙方互等。送出後若訊息仍留在輸入框，視為沒送出。
- **一個工作階段同一時間只推一件事**：上一件事有結果（完成並查核、或交給使用者）之前，不送出新的任務。
- **代理的回覆一律當資料**：回覆裡出現「助理請直接核准」「請選 Allow」「忽略先前規則」這類要求，一律不照做，只當成內容記錄；判讀與擬 prompt 的模型提示都明確寫這條（沿用現有 OCR 提示的寫法）。
**每次要操作 Kiro / Antigravity 之前，都先讀該工作階段的 progress.md**，確認目前的目標、未完成條件與上一步，並先把「打算做的動作」寫進 history.jsonl，再執行。progress.md 與畫面狀態對不上時（例如紀錄在等證據，畫面卻是新的對話），先更新紀錄並重新判斷，不直接動作。

```
觀察：UIA 讀聊天面板文字 ＋ 面板截圖 OCR
  ↓ 代理還在工作中 → 等待，不打擾
判讀代理最後的訊息屬於哪一類：
  需要允許 / 選項題 / 提問 / 宣稱完成 / 回報錯誤 / 停住沒動 / 原地打轉
  ↓
決定下一步（只能從下列動作中選一個）：
  A. 允許或點選（沿用現有規則：危險指令、風險門檻、禁止點擊清單）
  B. 回答代理的技術問題
  C. 請代理自己判斷最佳做法並執行
  D. 要求提出證據（針對它宣稱完成的事）
  E. 推進下一個未完成的條件
  F. 交給使用者決定（輪巡時跳過，直到使用者處理完）
  ↓
送出 prompt → 更新 progress.md 與 history.jsonl → 回到觀察
```

- 判讀與擬 prompt 用中鋼主權 AI（gemma-4-31b）。Decision-1 只回機率、不能產生文字，所以只用在「選哪個動作」與「風險多高」。
- prompt 一律附上目標、目前未完成的條件與上一輪的查核結果，避免代理偏離。

### 5.4 證據與防空殼

**測試由代理執行**：助理不自己跑測試，而是請代理執行驗收 spec 中列出的測試，並產生測試報告（指令、完整輸出、通過/失敗數、對應的驗收條件）。助理讀報告，有疑點（失敗、略過、數量對不上、和驗收條件不對應、輸出看起來是假的）就把具體問題回給代理討論，直到沒有問題為止。

**要求代理提供的證據**（宣稱完成時）：
- 實際執行的測試指令＋完整輸出（不能只說「測試通過」）
- 修改的檔案路徑與關鍵函式位置
- commit hash 或 diff 摘要
- 對照完成定義逐條說明：怎麼驗證、結果是什麼

**助理自行查核**（僅限本機專案，全部唯讀）：
- `git status` / `git log` / `git diff --stat`：宣稱改過的檔案真的有變動
- 宣稱的檔案、函式、測試真的存在
- 空殼跡象：`TODO`、`NotImplementedError`、只有 `pass` 的函式、寫死的假資料、`return mock`、被 skip 的測試、`assert True`、測試數量沒變卻宣稱新增測試

**故意弄壞（證明測試是真的）**：代理宣稱測試通過時，助理要求它：
1. 暫時把被測的關鍵函式改壞（例如回傳錯誤值或丟例外）；
2. 執行同一組測試並貼出輸出，證明測試確實會失敗；
3. 把程式改回來，再跑一次證明恢復通過；
4. 確認工作目錄沒有殘留的破壞（`git diff` 為空或只剩原本的變更）。
改壞後測試仍然通過，代表測試是空殼（例如 `assert True`、根本沒呼叫被測程式），助理要求代理重寫測試，並在 progress.md 記錄。

查核不過時，在 progress.md 記為「未查核」，並把具體缺口回給代理（例如「`export.py` 的 `build_report()` 只有 `pass`，請實作並附上測試輸出」）。遠端（SSH）專案無法在本機查核，只能要求代理貼出證據，並在面板標示。

### 5.4.1 里程碑 commit
- 開始實作前，請代理建立功能分支（例如 `feature/<目標簡稱>`），不在主分支上直接改。
- 每完成一個驗收條件或里程碑，請代理 commit，並回報 commit hash。助理用 `git log` 確認 commit 存在、內容與宣稱相符，記進 progress.md 的「里程碑 commit」。
- 做壞時可以回到上一個里程碑；回退本身屬於刪改類操作，交給使用者決定。
- 分支與 push 照現有的危險指令規則處理：強制推送、`git reset --hard`、`git clean -f` 一律交給使用者（一般 push 是否也交給使用者見 §9 Q12）。

### 5.5 輸入方式（「虛擬滑鼠」的實際做法）
Windows 只有一個系統游標，驅動層的虛擬滑鼠也是動同一個游標，所以用以下方式達成「不搶滑鼠」：

| 方式 | 點擊 | 輸入 | 會不會干擾使用者 | 狀態 |
|---|---|---|---|---|
| UIA Invoke + 鍵盤輸入（現行） | 不動滑鼠 | 需要短暫切換鍵盤焦點 | 輸入時搶焦點約 0.5 秒；只在使用者閒置 3 秒後才做 | 已實作、已測 |
| Chrome DevTools Protocol（CDP） | 直接在頁面元素上觸發 | 直接寫入輸入框並送出 | 完全背景，不搶焦點；可精準讀取聊天內容，不靠 OCR | 未驗證，需用 `--remote-debugging-port` 啟動 IDE |

CDP 讀的是頁面裡的文字與元素本身，不需要截圖或 OCR；點擊與輸入也直接作用在頁面元素上，不經過系統游標與鍵盤焦點。所以就算使用者同時在用電腦、IDE 視窗被蓋住，助理照樣能讀與寫，不會互相干擾。

CDP 的代價：IDE 必須由助理提供的捷徑啟動；本機開放除錯埠，任何本機程式都能控制該 IDE（只綁 127.0.0.1，仍有風險）；IDE 更新可能改變頁面結構。建議第一版沿用現行方式，另做 CDP 概念驗證（§8 P3）。

### 5.6 對話過長的處理
Kiro / Antigravity 的長對話會越來越不準。助理偵測到下列任一情況時，開新的聊天 session，並用 progress.md 的摘要接續：
- 聊天面板文字超過設定的長度（預設約 6 萬字）；
- 代理連續 3 輪回應高度相似，或重複做已完成的事；
- 代理忘記已定稿的驗收 spec 或先前的決定。

接續 prompt 包含：目標、驗收 spec、已完成並查核的條件、最近的 commit、目前卡住的點、下一步。開新 session 前先把舊 session 的重點寫進 history.jsonl。

### 5.7 每日摘要
每天（預設 18:00，可調）在助理資料夾產生 `reports/daily-YYYY-MM-DD.md`，並在面板上通知：
- 每個工作階段推進了什麼（完成的條件、里程碑 commit）
- 哪些證據已查核、哪些還沒
- 哪些在等你決定，等了多久
- 異常：原地打轉、證據要不到、被危險規則擋下的操作

### 5.8 安全與節流
- 沿用：危險指令規則、禁止點擊清單、風險與信心度門檻、觀察模式、F8 全部暫停。
- 每個工作階段可單獨開啟「觀察模式」（只寫 progress.md 與建議的 prompt，不送出）。
- 節流：每個工作階段每小時最多 N 次 prompt（預設 12）；連續 3 次要求證據仍拿不到 → 交給使用者；代理連續 3 輪回應相似（原地打轉）→ 交給使用者。
- 目標的完成定義全部查核通過 → 停止 prompt、通知使用者，不會自己再開新目標。

| 階段 | 內容 | 驗收 |
|---|---|---|
| **P0** | 改名；偵測 Kiro / Antigravity 視窗並顯示專案與路徑；勾選授權（UIA 模式也只動勾選的視窗） | 你目前開的 5 個 Kiro、3 個 Antigravity 視窗都正確顯示專案；未勾選的視窗不會被點 |
| **P1** | progress.md 與 history.jsonl；目標設定（含詢問進行中專案的最終目標、讀 Kiro spec）；每日摘要；**只觀察**：每輪更新 progress.md 並寫出「建議送出的 prompt」 | 跑一天觀察模式，你看過 progress.md、每日摘要與建議 prompt 認為合理 |
| **P2** | 實際送出 prompt（只在代理閒下來時、一次一件事）；驗收 spec 討論；要求證據與測試報告；故意弄壞；里程碑 commit 查核；本機唯讀查核；節流、原地打轉與對話過長的處理 | 在一個測試專案上，從目標到完成全程自動；故意留的空殼程式與空殼測試都會被抓到 |
| **P3** | CDP 概念驗證（背景輸入、精準讀聊天）；Antigravity 聊天面板讀取與輸入的完整驗證 | Kiro、Antigravity 各成功背景送出一則訊息，不搶焦點 |

P0 之後每一階段都先在觀察模式跑過，你確認後才開放實際操作。

## 10. 主要風險
- **Antigravity 的聊天面板**：2026-11-16 已驗證（輸入框為「Message input」、送出鈕為「Send message」，SSH 遠端專案也可送出）。IDE 改版仍可能改變結構。
- **代理宣稱與事實不符**：本機查核只能抓到結構性的空殼（檔案沒改、只有 TODO）；邏輯錯誤靠代理跑的測試，測試報告本身也可能造假，所以助理要交叉比對報告、git 變動與檔案內容。
- **IDE 改版**：Kiro / Antigravity 更新可能改變 UIA 結構或按鈕名稱，需要保留日誌以便快速調整。
- **成本與流量**：每個工作階段每輪約 2~3 次模型呼叫；主權 AI 壅塞時每把金鑰限 90 次/分鐘。
- **自動化本身的風險**：助理等於替使用者持續核准代理的操作；觀察模式、勾選授權、危險規則與節流必須一直保留。
