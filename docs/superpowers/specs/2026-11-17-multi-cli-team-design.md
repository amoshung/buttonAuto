# 設計：像素辦公室指揮多 CLI 的敏捷團隊

> 狀態：待使用者審閱（2026-11-17）。取代 `plans/2026-11-17-multi-cli-team.md` 草案中與本文件衝突的部分。
> 依據：recon\20261117-074209、recon\20261117-081433、recon\acp-20261117-082504.json、recon\model-bench-20261117-084841.md

## 1. 為什麼要做
使用者同時開發多個專案（常見 3 個以上），每個專案交給 AI 編碼 CLI 實作。目前要自己盯每個代理：按 Allow、回答問題、切對話、確認它真的做完。目標是讓**公司地端模型扮演敏捷團隊角色**，替使用者帶這些 CLI 一路做到「已驗證完成」，**盡量不需要使用者處理**，而且**每一關都有代理改不了的證據**。

### 目標
- 一個專案一間「房間」，房間數量不限，彼此平行。
- 角色（PO、Tech Lead、Scrum Master、QA、Reviewer）監督、對話、把關。
- 每一關以客觀證據過關：助理自己跑的測試、git 紀錄、diff 範圍、ACP 執行紀錄。

### 不做
- 不操作任何 IDE 視窗（不截圖、不 UIA、不搶焦點）。現有視窗驅動保留在程式裡、預設關閉。
- 不自架或改設定任何模型閘道；CLI 照用它們自己的登入與模型。
- 不替使用者做產品取捨。

### 反目標（技術上能跑但算失敗）
- 代理說「完成」就被當成完成。
- 兩個代理改到同一個檔案，或助理自動把東西合併進主線。
- 某間房在等慢模型思考時，其他房也跟著卡住。
- 「需要你」的事情散落各處、要使用者一間間找。

## 2. 限制與前提（偵察確認）
| 項目 | 結果 |
|---|---|
| kiro-cli 3.3.0 | `%LOCALAPPDATA%\Kiro-Cli\kiro-cli.exe`；已用公司 IAM Identity Center 登入；`kiro-cli acp` 交握成功，ACP 沿用 CLI 登入（不需 API key） |
| agy 1.5.9 | `%LOCALAPPDATA%\agy\bin\agy.exe`；`agy acp` 交握成功；登入狀態待第一個任務確認 |
| claude 2.1.326 | `~\.local\bin\claude.exe`；headless `-p`，無原生 ACP |
| PATH | 新裝的 CLI 不一定在舊視窗的 PATH 裡 → 程式一律從登錄檔讀最新 PATH 並以完整路徑啟動 |
| 模型 | glm-5.3（公司部署、免費）與 Decision-1（公司 LiteLLM、專用金鑰），兩者各用自己的金鑰；**不用 gemma-4-31b、muse-glimmer** |
| 使用者規範 | 一律非互動；Orchestrator 主控；同一時間禁止兩個代理改同一檔案；審查一律唯讀；交接 prompt 寫清背景、路徑、限制、輸出格式 |

## 3. 考慮過的做法
| 做法 | 取捨 | 結論 |
|---|---|---|
| A. 操作 IDE 的 agent 視窗（UIA＋截圖） | 能接手既有對話；但會搶焦點、怕改版、Antigravity 要截圖判讀、一個視窗一次只能顯示一個對話 | 不採用（保留為選用的舊對話接手） |
| B. **CLI 驅動：ACP 優先，headless 備援** | 結構化、不碰視窗、可平行、權限請求可逐一攔截；CLI 開的對話預設不出現在 IDE 視窗 | **採用**（使用者選定全走 CLI） |
| C. 經由 LiteLLM 統一接 CLI 與模型 | LiteLLM 只管模型不管指揮；Kiro／agy 綁自家服務無法改接 | 不採用（使用者決定） |

房間配置：一房一個實作者（使用者選定）；一房多實作者不採用（合併衝突、更多待決事項）。

## 4. 使用者看到的樣子

### 4.1 像素辦公室
```
 ‹  第 1 頁 ●○○  ›                                 你的桌子：收件匣 2
┌────────────────────┬────────────────────┐
│ _AI_Projs   ▮▮▮▯   │ MMI_Kernel ⚠ ▮▮▯▯  │  ← 需要你：整間房框變橘色
│ [K]實作  [A]審查    │ [A]實作  [C]審查    │
│ QA 在場             │ Tech Lead 在場      │
├────────────────────┼────────────────────┤
│ y6p2web2    ▮▮▮▮   │ bofmgr  排隊中      │
│ [C]實作  [K]審查    │ [K]實作  [A]審查    │
└────────────────────┴────────────────────┘
 走廊：PO · Scrum Master        頁碼點變橘色＝那一頁有事找你
```
- **房間＝專案**，一頁四間，左右滑動換頁；最後一頁永遠有一間「空房間」用來派工。
- 房間位置固定，不依狀態自動重排。
- 房內兩個座位：**實作**（一個 CLI）與**唯讀審查**（另一種 CLI，預設自動選不同家）。名牌字母與顏色代表 CLI（K＝kiro-cli、A＝agy、C＝claude）。
- 牆上四段條＝關卡進度：目標 → 驗收 spec → 實作與查核 → 審查與完成。
- 角色是共用團隊，平時在走廊；輪到誰出手就走進該房間；**同一角色一次只在一間房**（如實呈現排隊）。
- 收件匣集中所有「需要你」；點一下跳到該房並打開詳情。
- 房間狀態：運作中／排隊中（超過同時運作上限）／等你／暫停／已完成（封存，移出畫面）。

### 4.2 派工流程
1. 點空房間 →「派工」→ 從清單選專案資料夾（Kiro／Antigravity 開過的專案自動列出），或貼路徑。**資料夾是唯一必填。**
2. 系統掃描約 5 秒，顯示「我看到的現況」：`progress.md` 的目前任務與進度、最近的計畫／規格檔（`docs/plans`、`.kiro/specs`、`*plan*.md`）、git 分支與未提交改動。
3. 選工作來源（三選一）：接續 `progress.md` 的目前任務／從掃描到的規格檔挑一份／自己打一句目標。
4. 選陣容：實作 CLI、審查 CLI（預設另一家）、自主程度、可修改範圍（預設整個 repo，排除 `.git` 與金鑰檔）。
5. PO 起草驗收條件 → 使用者按「開工」（自主程度「積極」時自動開工）。
6. 運作中：見 §5、§6。
7. 交付：全部關卡通過 → 功能分支上有 commit 與證據 → **使用者按「合併」才併入主線**。

### 4.3 檔案放哪裡
| 內容 | 位置 | 誰寫 |
|---|---|---|
| 專案現有進度 | 專案的 `progress.md` | 使用者與代理（助理只讀；代理在功能分支上更新它） |
| 規格、計畫、證據 | 專案的 `docs/ai-team/<任務名>/`（spec.md、plan.md、evidence.md） | 助理，跟著功能分支提交 |
| 執行狀態（房間、對話 ID、歷史） | buttonAuto 的 `sessions/` | 助理（不進專案） |
| 工作目錄 | `<專案>/../.ai-team-worktrees/<專案>-<任務名>/`（git worktree） | 實作 CLI |

## 5. 角色與關卡
| 關卡 | 主責角色 | 過關證據 |
|---|---|---|
| ① 目標與驗收條件 | PO | 每條條件附可執行的檢查指令；glm-5.3 審查具體度；使用者確認或自動採用 |
| ② 計畫 | Tech Lead | 計畫逐條對應驗收條件（程式檢查無遺漏）；寫出 allowed_paths |
| ③ 實作 | Scrum Master | 功能分支上的 commit 存在；diff 不超出 allowed_paths；無 TODO、空殼、被略過的測試 |
| ④ 測試 | QA | **助理自己在 worktree 跑測試**看結束碼與通過數；故意弄壞一處，測試必須失敗 |
| ⑤ 審查 | Reviewer＋審查座位的 CLI（唯讀） | 對照計畫與驗收條件審 diff，意見彙整進 evidence.md |
| ⑥ 完成 | — | ①～⑤ 全部通過，等使用者按合併 |

**對齊對話**
- 代理工作中：只觀察，累積偏離訊號（改計畫外檔案、重複同一個失敗指令、做範圍外功能、久未 commit、回覆塞滿工具流水帳）。
- 代理停下來，或偏離訊號累積：對應角色開口。訊息署名（例 `【QA】`），附目標、目前第幾條、上一關查核結果。
- 不定時閒聊；每房每小時送出訊息有上限。
- 對話過長或原地打轉：開新對話並帶進度摘要接續。

**權限請求（ACP）處理順序**
1. 危險指令規則（現有 `deny_patterns`）命中 → 交給你。
2. 唯讀操作（讀檔、搜尋、列目錄）→ 直接允許。
3. 其餘 → §6 的允許判斷。
headless（claude）無法逐一攔截，靠 worktree 隔離＋事後 diff 與測試把關。

## 6. 模型分工（依 recon\model-bench-20261117-084841）
| 工作 | 模型 | 依據 |
|---|---|---|
| 允許判斷（主） | **Decision-1** | 4／4 正確；0.5～1.4 秒；機率經校準、分得很細 |
| 允許判斷（第二意見） | glm-5.3 低思考量 | 4／4 正確；0.7～2.3 秒。Decision-1 落在灰色地帶（風險 0.3～0.7 或目標相關 0.2～0.8）時才問；兩者都說安全才代按，意見不一就交給你 |
| 是非題快判（是否偏離、是否該要證據、選項題選哪個） | Decision-1 | 只回機率、便宜；判定「需要開口」時才請 glm 寫訊息 |
| 角色對話（寫訊息、回答代理提問、要求證據、拉回目標） | glm-5.3 低思考量 | 3.9～5.8 秒，內容具體可執行 |
| 重大審查（驗收 spec 定稿、合併前審 diff） | glm-5.3 一般思考量 | 40～105 秒、延遲不穩；只在這兩個時點用，逾時改用低思考量 |
| 任一模型無法使用 | 另一個模型＋更保守門檻；兩者都不行就暫停自動處理、交給你 | — |

**避免卡頓**
- 每間房各自運作；兩個模型各有工作佇列與同時呼叫上限（初始 Decision-1：8、glm 低：4、glm 一般：1）。
- 允許請求走快速通道，不排在角色對話後面。
- 角色思考用當下快照在背景進行，代理不必等；提醒排隊到代理下次停下來再送。
- 同時「運作中」的房間上限預設 4，超過的房間「排隊中」；設定可調。
- 逾時：glm 低 30 秒、glm 一般 150 秒、Decision-1 10 秒；壅塞時逐次拉長重試間隔。

## 附錄 A（2026-11-17 09:02 使用者追加）：glm 員工、Decision-1 派工、用量備援

### A1. 新的辦公室人員（座位）
| 座位 | 實際執行 | 用途 | 費用 |
|---|---|---|---|
| Kiro | `kiro-cli acp` | 實作／審查 | 依公司額度 |
| Antigravity | `agy acp` | 實作／審查 | 依 Google 額度 |
| Claude | `claude -p`（自己的登入） | 實作／審查 | 依訂閱額度 |
| **GLM（一般）** | `claude -p`，環境變數 `ANTHROPIC_BASE_URL=<litellm base_url>`、`ANTHROPIC_AUTH_TOKEN=<glm key>`、`ANTHROPIC_MODEL=glm-5.3`，不帶思考預算 | 實作／審查；**用量備援的接手者** | 免費 |
| **GLM（高思考）** | 同上，加 `MAX_THINKING_TOKENS=16000` | 規格定稿、困難除錯、合併前審查 | 免費但慢 |

- GLM 座位借用 Claude Code 當「手腳」（讀寫檔、跑指令、工具呼叫），腦袋換成公司 glm-5.3。這是呼叫公司既有的 LiteLLM 端點，不是自架閘道（符合「不用 LiteLLM 管 CLI」的決定：Kiro／agy／Claude 自己的登入完全不動）。
- 前提要冒煙驗證：公司 LiteLLM 需提供 Anthropic 格式的 `/v1/messages`。驗證失敗 → GLM 座位標示「不可用」，用量備援改為「暫停等待額度」並通知使用者。
- 技能：GLM 與 Claude 座位可載入 compound-engineering（`--plugin-dir <設定的外掛路徑，資料夾或 .zip>`）與 Serena（`--mcp-config` 臨時檔：`uvx --from git+https://github.com/oraios/serena serena start-mcp-server --context claude-code --project <worktree>`）。找不到外掛路徑或 `uvx` → 略過並記錄，不算錯誤。Kiro／agy 不注入（它們有自己的設定）。

### A2. Decision-1 當派工主管（我的建議）
規則先決定「誰可以」，Decision-1 只在可行選項中挑「誰最適合」，避免模型做出不可能的選擇：
1. **可行性（規則）**：CLI 已安裝、未被標為用量已滿、審查者≠實作者、GLM 座位冒煙通過。
2. **難度判斷（Decision-1 機率題）**：「此任務需要跨多檔重構或深入除錯嗎？」→ p_complex。
3. **選模型等級**：每階段預設 —— 規格：standard；計畫：standard；實作：p_complex ≥ 0.7 → premium，≤ 0.3 → economy，其餘 standard；小修正（同一 issue 第 1 次）：economy；審查：standard；合併前最後審查：GLM 高思考（免費）。
4. **選 CLI**：可行座位中，分數 = Decision-1「<座位> 適合這個任務嗎」的機率 − 成本權重 × 該等級相對成本；GLM 成本 0，所以簡單任務自然落到 GLM，困難任務才花付費額度。成本權重預設 0.3，可調。
5. 使用者在派工精靈仍可手動指定（指定就不再自動選）。

模型目錄 `team_models.json`（可編輯、不含金鑰）：每座位列出 `{id, tier: economy|standard|premium, cost}`。預設：claude＝haiku／sonnet／opus（cost 1／3／15）；kiro、agy＝`auto`（standard，cost 2），使用者可補具體模型 id；GLM＝glm-5.3（cost 0）。

### A3. 用量已滿 → 全部改用 GLM 一般，恢復後切回
- 偵測：驅動錯誤、代理訊息或程序結束文字命中 `quota|rate limit|usage limit|limit reached|credits|exceeded|429|too many requests|額度|用量`（不分大小寫），且當回合失敗。能解析出重置時間（如 `resets at 3pm`、`try again in 2 hours`）就用，否則 60 分鐘後試探。
- 處理：該 CLI 標為「已滿」（全辦公室共用狀態），所有用它的房間在**目前回合結束時**改由 GLM（一般）接手：新開 GLM 驅動、送交接摘要（目標、條件、已完成 commit、最後一則問題），房間記錄 `fallback_from`。不進收件匣（不打擾使用者），只記事件並在畫面上顯示。
- 恢復：每 30 分鐘（或到重置時間）用最便宜的模型送一則極短試探；成功 → 標為可用，房間在**下一個階段邊界**切回原 CLI（不在實作中途換手，避免半套改動）。
- 審查座位已滿 → 同樣改由 GLM 唯讀審查。
